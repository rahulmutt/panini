# Curādi gaṇa (gaṇa 10), slice 10i — the āsvadīya: 10.0499, with 2565 and 2571

## Summary

10h's "Later slices" list put the āsvadīya next: the gaṇasūtra 10.0499
*ā svadaḥ sakarmakāt* makes ṇic optional for the 59 rows from
`10.0279 grasa~` to `10.0337 svAda~`. This slice curates all 59, and with
them the last two reachable one-row optional-ṇic triggers: 2565 (`pF`) and
2571 (`Guzi~r`). Every one of the 61 rows is `PadaAssignment::Nic`.

10h's fork carries most rows unchanged. Three things are new:

- the gaṇasūtra 10.0499 and the Kaumudī triggers 2565 and 2571, as
  optional-ṇic vikalpas in vidyut's check order;
- 3.1.28 *gupūdhūpavicchipaṇipanibhya āyaḥ* (√dhūp, √vich), on the ṇic-less
  branch;
- a second 6.1.73 *che ca* entry, in sanādi before guṇa (√vich).

A throwaway prototype built all of this and audited it against vidyut
(Evidence): zero differences across the whole corpus, and every
pre-existing root's trace byte-identical.

### Decisions

**10.0499, 2565 and 2571 are `skip_nic` vikalpas in vidyut's check order.**
Each is keyed on the row's `OPTIONAL_NIC` entry, with 2564's bars
(`3.1.25`, `2573.2`). 10.0499 sits after 10.0498 and before 2564, 2565
after 2564, and 2571 after 2570, matching `dhatu_karya.rs`. So the idit
rows (`tuji~`, `ahi~`, …) credit 10.0499, never 2564; the udit `vftu~` and
`vfDu~` never 2570; `pUrI~` never 2572. 10.0499 is a dhātupāṭha gaṇasūtra,
numbered as vidyut numbers it (`DP("10.0499")`), like 10.0496 to 10.0498;
2565 and 2571 are Kaumudī ids, like 2564.

**`optional_nic_from_upadesha` learns the range and the two triggers.**
After the 10.0498 range check it returns `"10.0499"` for any row in
`10.0279..=10.0337`, before reading markers. Among the marker checks,
after idit, it returns `"2565"` for an upadeśa ending in `F`. After
ñit/udit, it returns `"2571"` for `Guzi~r`. The exclusion assertion in
`optional_nic_matches_upadesha_markers` narrows to `10.0368` alone, and the
helper's doc drops its "this reading would be wrong" caveat.

**3.1.28 *gupūdhūpavicchipaṇipanibhya āyaḥ* is a sanādi rule on the
ṇic-less branch, keyed by row number.**
- **What it does:** on the ṇic-less branch of `DUp` and `viC` it adds the
  pratyaya āya, giving *dhūpāyati* and *vicchāyati*. vidyut adds it as a
  sanādi pratyaya after 10.0499 declines ṇic (`sanadi.rs`; trace
  `10.0499 → 3.1.28 → 3.4.114 → 3.1.32`).
- **Why a table:** vidyut keys it on the upadeśa (`gupU~`, `DUpa~`,
  `viCa~`, `paRa~\`, `pana~\`), in any gaṇa. Root text cannot decide it
  here: curādi `10.0302 gupa~` stores as `gup`, the same code as bhvādi
  `gupU~`, but takes no āya. So `panini-data` gains a number-keyed list,
  `AYA = ["10.0303", "10.0304"]`, on the `MRJ` / `JNAPADI` precedent. The
  aṅga is tagged `Tag::Aya` from it.
- **The data test:** `AYA` is exactly the curated rows whose vendored
  upadeśa is in vidyut's five-entry list. This is non-circular, as
  `optional_nic_matches_upadesha_markers` is.
- **The changes 3.1.28 forces elsewhere:** 3.4.114 *ārdhadhātukaṃ śeṣaḥ*
  and 3.1.32 *sanādyantā dhātavaḥ* learn to take the āya term. 3.1.32 sets
  `Tag::Nijanta` only when the folded pratyaya is ṇic, not āya.
- **Its pin:** it is not a vikalpa (3.1.31 is out), so it joins the
  rule-order pin, not the vikalpa list.

**6.1.73 *che ca* runs a second time, in sanādi, before the sanādi 7.3.86.**
- **The problem:** on √vich, tuk must precede guṇa. Without it the ṇic
  branch gives *vechayati*, and vidyut gives *vicchayati*
  (`angasya.rs`: "tuk-Agama can block guna"; trace
  `3.4.114 → 1.4.13 → 6.1.73 → 3.1.32`). The ṇic-less āya branch takes the
  same tuk (*vicchāyati*).
- **The new entry:** a second `Rule` with id `6.1.73` in `SANADI`, the
  precedent 10h set with 6.1.78. Its apply function is the same function
  as the `ANGA_RULES` entry, the `word_chars` scan over the whole word, and
  is shared, not copied.
- **Why the whole-word scan:** the prototype scanned only the aṅga, which
  the existing entry's comment rules out. That narrowing would need an
  argument that a `C` can only be root-initial, the kind of argument that
  has twice cost this repo a real defect.
- **The existing entry:** the laṅ-aṭ entry in `ANGA_RULES` stays where it
  is. On √vich it finds the `C` already preceded by `t` and declines.
- **Tests:** tests that look 6.1.73 up by id scope the lookup to the stage
  static. The prototype found `anga.rs`'s
  `che_ca_inserts_tuk_only_after_a_short_vowel` shadowed by the new entry.

**Both `laGi~` rows are curated: the uniqueness check names the pair.**
- **The conflict:** `10.0291` and `10.0327` are identical upstream:
  upadeśa, artha (`BAzAyAm`) and 10.0499 verdict. So
  `dhatupatha_numbers_resolve_upstream`'s sibling count finds two.
- **The decision:** the dhātupāṭha lists the root twice, vidyut derives
  both, and curādi can only close at 509 of 509 with both curated. The
  test therefore allows exactly two siblings for exactly this pair. The
  exception is named in a constant with a comment, and a pin asserts the
  pair is still identical upstream.
- **The alternative, rejected:** curating `10.0291` only leaves a row no
  slice can ever curate.
