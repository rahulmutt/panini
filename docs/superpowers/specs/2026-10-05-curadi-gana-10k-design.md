# Curādi 10k: the plain obligatory-ṇic rows

10j's "Later slices" list puts the plain obligatory-ṇic hal-anta rows next:
about 165 of them across `10.0006`–`10.0191` and `10.0237`–`10.0278`, plus
seven stragglers. Its instruction was to prototype-audit them first, since no
spec had examined them.

The prototype (Evidence) curated all **164** such rows and audited them
against vidyut. 155 match vidyut in every cell, with no engine change. The
other 9 need six rule changes and one data entry. They go to slice 10l
(Later slices), which the prototype's findings already scope.

This slice curates the 155. It is a data-only slice: no engine change and no
new rule id. After it, curādi is **open at 482 of its 509** rows; 10l's nine
would bring it to 491.

  parT` (by ṛ-guṇa), `10.0090`/`10.0131` (both `pula~`),
  `10.0098 pAl`/`10.0099 pal` (by 7.2.116), and `10.0051`/`10.0052` (below).

Each row's comment names its partner.

**`10.0051 zAntva~` and `10.0052 sAntva~` are both in, as a pinned
exception.** 6.1.64 *dhātvādeḥ ṣaḥ saḥ* makes `zAntva~` `sAntv`, the same as
`sAntva~`, with the same artha *sAmaprayoge*. So
`dhatupatha_numbers_resolve_upstream`'s sibling check reads each as
ambiguous. The prototype failed exactly there.

- A second named exception, `CONVERGENT_UPADESHA_PAIR = ["10.0051",
  "10.0052"]`, joins `IDENTICAL_UPSTREAM_PAIR`, and each row is allowed the
  other as its one sibling.
- Unlike the identical pair, these upadeśas differ. A new assertion pins how:
  identical but for the first character, `z` in `10.0051` and `s` in
  `10.0052`. So the exception cannot absorb a different collision.
- `SraR` (`10.0063`/`10.0174`) and `arh` (`10.0257`/`10.0367`) also share
  code and artha, but the check already separates them by optional-ṇic
  verdict. They need nothing new.
